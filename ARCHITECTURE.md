# VoiceChat EFL — Architecture & Developer Guide

A task-based AI English conversation platform built for Korean secondary school students. Teachers author tasks; students have real-time spoken conversations with an AI partner that adapts to their level, interests, and learning style; post-session written feedback is generated automatically in Korean.

## 1. Educational Framework

### Target Context
Korean EFL (English as a Foreign Language) high school students who have strong receptive English skills from test prep but little authentic speaking experience. The app tries to replicate the benefits of a private conversation tutor at scale.

### Theoretical Grounding

The conversation AI's behaviour is shaped by four SLA (Second Language Acquisition) principles baked directly into every system prompt:

| Principle | What the AI does |
|---|---|
| **Comprehensible Input** (Krashen i+1) | Vocabulary and sentence complexity scale to the student's declared CEFR level. Beginner gets A1–A2 words only; advanced gets hedging language and collocations. |
| **Pushed Output** (Swain) | Question strategies are tuned per level. Beginners get yes/no or forced-choice questions to lower the barrier. Intermediate+ get open questions that require a full sentence answer. |
| **Recasting** | When the student makes a grammar error the AI quietly models the correct form in its reply without ever naming the error. ("You went there last week! What was it like?") |
| **Scaffolding** | If the student is stuck, the AI offers a hint ("Maybe the word you're looking for is…?") rather than waiting silently. |
| **Affective Filter** (Krashen) | The AI is explicitly instructed to keep anxiety low, praise effort, and never act like a teacher correcting a student. |

### Alignment with 2022 Korean National English Curriculum (영어과 교육과정)
Learning objectives generated by AI analysis are grounded in the curriculum's 의사소통 기능 (communicative function) taxonomy: describe, express opinions/feelings, ask for and give information, talk about experiences/plans, compare, suggest. Objectives take the form `Students can [function verb] [specific content] [using X]` — observable, task-based, and tied to a linguistic vehicle.

### Learning Style Adaptation
Students choose from four VAK-adjacent learning styles. The system prompt includes a dedicated behaviour block per style:

- **Visual** — vivid imagery, scene-painting, spatial analogies
- **Auditory** — explicit pronunciation modelling, invitations to repeat phrases aloud
- **Reading/Writing** — precise word definitions when introducing vocabulary, rephrasing student output in better English
- **Kinesthetic** — experience-anchored questions, role-play scenarios, action verb framing

### Silence / Short-Response Support
After two consecutive empty or very-short (< 4-word) responses, a suggestion bubble appears offering sentence starters ("I think…", "In my opinion…", "Can you say that again?"). This addresses the inhibition many Korean students feel about speaking before they have a complete thought.

## 5. Database Schema

Three tables, SQLite-compatible (runs on Turso in production, local file in dev).

```sql
CREATE TABLE teachers (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  code       TEXT UNIQUE NOT NULL,   -- uppercase access code used for login
  name       TEXT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE tasks (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  teacher_id          INTEGER NOT NULL REFERENCES teachers(id),
  title               TEXT NOT NULL,
  topic               TEXT,
  objectives          TEXT,   -- JSON: ["Students can describe...", ...]
  vocabulary          TEXT,   -- JSON: ["word", ...] or [{word, definition}, ...]
  language_forms      TEXT,   -- JSON: ["look forward to doing", "past continuous (was/were + V-ing)", ...]
  persona_name        TEXT DEFAULT 'Alex',
  persona_description TEXT,
  active              INTEGER DEFAULT 1,
  created_at          DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE sessions (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id         INTEGER NOT NULL REFERENCES tasks(id),
  student_name    TEXT NOT NULL,
  level           TEXT,      -- beginner | elementary | intermediate | upper-intermediate | advanced
  interests       TEXT,      -- JSON: ["music", "sports", ...]
  learning_style  TEXT,      -- visual | auditory | reading | kinesthetic
  conversation_id TEXT,      -- reserved (ElevenLabs agent ID, not currently used)
  transcript      TEXT,      -- JSON: [{role:"user"|"agent", message}]
  outline         TEXT,      -- JSON: {beats:[{turn, phase, goal, ai_cue, vocab_target, form_target}]}
  feedback        TEXT,      -- JSON: post-session feedback object (written after end)
  started_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
  ended_at        DATETIME
);
```

`outline` and `feedback` were added as `ALTER TABLE` migrations inside `ensureReady()` to preserve existing rows.

## 6. API Reference

All routes are under `/api`. The server is a single Express app mounted at `api/index.js` for Vercel.

### Teacher / Task Routes (`/api/teachers`)

| Method | Path | Description |
|---|---|---|
| POST | `/teachers/login` | `{code}` → returns teacher row |
| POST | `/teachers/register` | `{name, code}` → creates teacher |
| GET | `/teachers/:id/tasks` | List tasks for teacher |
| POST | `/teachers/:id/tasks` | Create task |
| PUT | `/teachers/:id/tasks/:taskId` | Update task |
| DELETE | `/teachers/:id/tasks/:taskId` | Delete task |
| GET | `/teachers/:id/tasks/:taskId/sessions` | Session history with transcripts and feedback |

### Session Routes

| Method | Path | Description |
|---|---|---|
| GET | `/tasks` | List all active tasks (student task picker) |
| POST | `/start` | `{task_id, student_name, level, interests, learning_style}` → creates session, generates outline, returns `session_id` |
| POST | `/:sessionId/end` | `{transcript, conversation_id}` → saves transcript, marks ended |

### AI Routes

| Method | Path | Description |
|---|---|---|
| POST | `/chat` | `{session_id, messages, speech_speed}` → Gemini response text |
| POST | `/feedback/:sessionId` | Generates and saves Korean post-session feedback |
| POST | `/tasks/analyze` | `{text}` → extracts title, topic, objectives, vocabulary, language_forms |
| POST | `/stt` | Multipart audio → `{text}` via ElevenLabs Scribe |
| POST | `/tts` | `{text, voice_id, speed}` → audio/mpeg stream |

## 7. Conversation Pipeline (turn-by-turn)

```
Student holds PTT button
        │
        ▼
MediaRecorder captures audio (webm or mp4)
        │
        ▼
POST /api/stt  (ElevenLabs Scribe v1)
  - keyterms from task vocabulary for better recognition
  - returns {text}
        │
        ▼
Empty / < 4 words? ──yes──▶ increment silenceCount
        │                    ≥ 2 consecutive? → show suggestion bubble
        │ no
        ▼
Append to messagesRef (Gemini format) and transcriptRef (display format)
        │
        ▼
POST /api/chat  (Gemini 2.5 Flash)
  - session_id: loads task + student from DB
  - messages: full conversation history
  - speech_speed: passed through to prompt builder
  - returns {text}
        │
        ▼
Append AI turn to both refs, update transcript display
        │
        ▼
POST /api/tts  (ElevenLabs Flash v2.5)
  - voice_id: chosen by student
  - speed: numeric 0.70–1.00
  - streams audio/mpeg back
        │
        ▼
Play audio via Web Audio API
status → idle → ready for next turn
```

### Status Machine

```
connecting → idle → recording → processing → speaking → idle → ...
                                           ↘ idle (on empty STT)
```

The push-to-talk button is disabled during `processing` and `speaking` to prevent overlapping turns.

## 8. System Prompt Engineering

`server/utils/promptBuilder.js` generates a fresh system prompt for every `/api/chat` call. It takes task metadata, student profile, turn count, speech speed, and the current conversation beat.

### Prompt Structure

```
[Persona declaration]
  "You are {persona_name}, a warm and genuinely curious person..."

[Current phase block]  ← changes every turn
  Either:
  (a) Beat-based: specific goal + opening cue + vocab/form targets
  (b) Warm-up fallback (turns 0–2): build rapport only, no lesson content
  (c) Bridge fallback (turns 3–4): transition to topic
  (d) Task engagement fallback (turns 5+): full task engagement

[SLA Techniques]
  1. Comprehensible Input   — vocabulary ceiling per CEFR level
  2. Pushed Output          — question strategy per level
  3. Recasting              — quiet error correction by example
  4. Scaffolding            — hints when student is stuck
  5. Affective Filter       — keep anxiety low

[Learning style block]  ← only present if style is set
  Visual / Auditory / Reading / Kinesthetic behavioural instructions

[Response format]
  - Max sentence count per level
  - Pacing instruction from speech speed
  - Always end with exactly one question
  - PLAIN SPEECH ONLY — no emoji, markdown, or asterisks (output goes to TTS)
  - Never reference lesson meta-vocabulary ("objective", "language form", etc.)
```

### Level-Specific Constraints

| Level | CEFR | Max sentences | Question strategy |
|---|---|---|---|
| Beginner | A1 | 2 (< 10 words each) | Yes/no or forced choice |
| Elementary | A2 | 2 | Simple open questions |
| Intermediate | B1 | 3 | Open, invite 1–2 sentence answer |
| Upper-Intermediate | B2 | 3 | "Can you explain why?" |
| Advanced | C1+ | 3 | Push for precision and depth |

## 9. AI Outline Generation

At session start (`POST /api/start`), before inserting the session row, Gemini generates an **8-beat conversation outline** for the entire session. This is the planning step.

### Beat Schema

```json
{
  "beats": [
    {
      "turn": 1,
      "phase": "warmup",
      "goal": "Build rapport by asking about student's interests",
      "ai_cue": "Hey Jihoon! Have you been watching anything good lately?",
      "vocab_target": null,
      "form_target": null
    },
    {
      "turn": 5,
      "phase": "task",
      "goal": "Elicit past continuous to describe an ongoing past action",
      "ai_cue": "So when you arrived at the party, what was everyone doing?",
      "vocab_target": "looking forward to",
      "form_target": "past continuous (was/were + V-ing)"
    }
  ]
}
```

### Beat Distribution Rule
- Beats 1–2: warm-up only (student interests, no lesson content)
- Beat 3: bridge from student's world to lesson topic
- Beats 4–8: task engagement, one vocabulary word introduced per beat, each language form gets a dedicated beat with a question that forces that form as the natural answer

The outline is stored in `sessions.outline` (JSON). Each call to `/api/chat` looks up the beat matching `turnCount` and passes it to `promptBuilder`. If no outline exists (e.g. Gemini failed), the prompt falls back to phase-based logic.

## 10. Post-Session Feedback

Triggered by the student clicking "End Chat". After saving the transcript, the client calls `POST /api/feedback/:sessionId`.

### What the Feedback LLM Receives
- Student name and CEFR level
- Language forms they were practicing (from task)
- Vocabulary they were practicing
- All student utterances (numbered)

### Selection Logic
The prompt instructs Gemini to select **up to 3 utterances** worth commenting on, prioritising:
1. Utterances that attempt target language forms
2. Utterances with notable grammar (correct or incorrect)
3. Utterances that use target vocabulary

### Output Schema (all explanatory text in Korean)

```json
{
  "overall": "전체 피드백 2문장 — 한국어",
  "sentences": [
    {
      "original": "exact student utterance in English",
      "what_worked": "긍정적 피드백 — 한국어",
      "needs_improvement": "개선 포인트 — 한국어",
      "corrected": "natural improved version in English"
    }
  ]
}
```

### Short Utterance Rule
If an utterance is 3 words or fewer (single words, fillers like "yeah", "ok"), `what_worked` is replaced with a fixed Korean message: "이 표현은 너무 짧아요. 다음번에는 완전한 문장으로 말해 보세요." The improvement and corrected fields are still generated.

### Language Choice Rationale
- `original` and `corrected` are always English — students need to see and internalise the correct English form
- `what_worked`, `needs_improvement`, `overall` are always Korean — instructional explanation is more accessible and actionable in the student's L1

## 11. Teacher Dashboard

### Authentication
Code-based, no passwords. Teachers register with a name and a self-chosen uppercase code. Login is just `POST /teachers/login` with that code. State is persisted in React via `localStorage` (via App.jsx `teacher` state) for the session.

### Task Creation
Two paths:
1. **Manual** — fill in title, topic, objectives (one per line), vocabulary (comma/line separated), language forms (grammar pattern formulas, one per line)
2. **AI-assisted** — paste any text (textbook paragraph, article, dialogue). Gemini extracts:
   - `title` — 3–6 word lesson title
   - `topic` — 1–5 word topic phrase
   - `objectives` — 3–4 curriculum-aligned can-do statements
   - `vocabulary` — 8–12 key words/phrases
   - `language_forms` — 2–4 grammar pattern formulas (e.g. `look forward to doing`, `past continuous (was/were + V-ing)`)

### Language Forms Format
Language forms are stored and displayed as **pattern formulas**, not example sentences. This is pedagogically important: the formula (`look forward to doing`) tells the AI exactly what structure to elicit, and is more concise for the teacher to read and edit than a full sentence.

### Session Viewer
Teachers can view per-task sessions showing:
- Student name, level, timestamp
- Full turn-by-turn transcript
- AI-generated feedback (collapsed by default, expandable)

## 12. Student Onboarding Flow

Three steps before the conversation starts:

**Step 1 — Name**
Simple text input. Personalises all AI greetings.

**Step 2 — Task selection**
Fetches all `active = 1` tasks from the database. Displayed as cards with title, topic, and teacher name.

**Step 3 — Profile**
- **CEFR level** — slider (A1 → C1+). Defaults to B1 (Intermediate). Automatically sets speech speed to 75% for A1/A2, 90% otherwise.
- **Voice** — 2×2 grid of 6 voices: 2 American, 2 British, 2 Australian (all ElevenLabs Flash v2.5 voice IDs)
- **Speech speed** — continuous slider 70%–100% with live percentage badge
- **Interests** — free text, comma-separated (used to personalise warm-up beats)
- **Learning style** — 4-option card grid (Visual / Auditory / Reading / Kinesthetic)

All profile data is passed to `POST /api/start` and stored in the session row. It shapes the system prompt for the entire session.

## 13. Deployment

### Architecture on Vercel
The entire backend is a single Vercel Serverless Function at `api/index.js` which exports the Express app. All `/api/*` requests are rewritten to it; all other requests serve the Vite-built SPA from `client/dist`.

```json
// vercel.json
{
  "rewrites": [
    { "source": "/api/(.*)", "destination": "/api" },
    { "source": "/(.*)",     "destination": "/index.html" }
  ],
  "functions": {
    "api/index.js": {
      "maxDuration": 30,
      "includeFiles": "server/db/schema.sql"
    }
  }
}
```

`includeFiles` ensures `schema.sql` is bundled with the function so `ensureReady()` can read it at cold start.

### Database
- **Production**: Turso hosted LibSQL (`libsql://...turso.io`). Persistent across all function invocations.
- **Development**: Local LibSQL file at `server/db/voicechat.db`. Created automatically.

`database.js` checks for `TURSO_DATABASE_URL` at startup and routes accordingly.

### CORS
The server detects `process.env.VERCEL` and sets `Access-Control-Allow-Origin: *` on Vercel, or the configured `CLIENT_ORIGIN` locally. This is safe because all sensitive routes are protected by API keys on the server side.

## 15. Key Design Decisions

### Why a single Vercel Function for all routes
Simpler deployment and zero cold-start penalty on hot routes. The 30-second timeout is enough for TTS streaming and Gemini calls. Avoids Vercel's per-function config sprawl.

### Why Turso (hosted LibSQL) instead of Postgres
SQLite semantics are simpler (no connection pooling, no migrations tooling needed), the data model is small, and Turso's LibSQL is wire-compatible with `@libsql/client`. The alternative (Vercel-hosted Postgres) would have been heavier to set up and more expensive at low volume.

### Why Gemini 2.5 Flash with `thinkingBudget: 0`
The chat responses must be fast enough not to break the conversational flow — students are waiting for the AI to respond before they can speak again. Setting `thinkingBudget: 0` disables chain-of-thought reasoning and cuts latency significantly. The feedback and planning calls use slightly higher token budgets where latency matters less.

### Why push-to-talk instead of voice activity detection
VAD (Voice Activity Detection) requires either a local WASM model or a persistent WebSocket. PTT is simpler, works on all mobile browsers, and is actually closer to real conversation rhythm — you think, then you speak.

### Why `thinkingBudget: 0` in feedback too
The feedback JSON is structured and constrained. Thinking mode adds latency without improving the quality of per-sentence grammar notes. Kept off for all three LLM uses.

### Why learning style in the system prompt rather than stored in the session
It is stored in the session. The session row includes `learning_style`. At each chat turn, `promptBuilder` reads it from the DB row and includes the appropriate behaviour block. This means the style influences every single turn of the conversation, not just the initial setup.

### Why plain CSS instead of Tailwind / a component library
The UI is small (3 pages + modals). A utility framework would add 30KB+ for marginal productivity benefit at this scale. Custom CSS variables make theming trivial.

## 16. Replication Guide

### Minimum Viable Clone

1. **Get API keys** for ElevenLabs (STT + TTS) and Google AI Studio (Gemini)
2. **Create a Turso account**, run `turso db create your-app`, get URL and token
3. **Clone and install:**
   ```bash
   npm install
   npm install --prefix server
   npm install --prefix client
   ```
4. **Copy `.env`** in `/server`:
   ```
   ELEVENLABS_API_KEY=sk_...
   GEMINI_API_KEY=AIza...
   TURSO_DATABASE_URL=libsql://your-db.turso.io
   TURSO_AUTH_TOKEN=eyJ...
   CLIENT_ORIGIN=http://localhost:5173
   PORT=3001
   ```
5. **Start dev servers:**
   ```bash
   # Terminal 1
   cd server && npm run dev

   # Terminal 2
   cd client && npm run dev
   ```
6. **Deploy to Vercel:**
   ```bash
   vercel --prod
   # Add env vars:
   vercel env add ELEVENLABS_API_KEY production
   vercel env add GEMINI_API_KEY production
   vercel env add TURSO_DATABASE_URL production
   vercel env add TURSO_AUTH_TOKEN production
   ```

### Swapping the LLM
All three AI routes (`chat.js`, `feedback.js`, `analyze.js`, `sessions.js`) call the Gemini REST API directly with `fetch`. To swap to a different provider, change the `GEMINI_API` URL and request/response shape in each file. The system prompt format (plain text instructions) works with any model.

### Swapping the TTS / STT
- TTS: replace `tts.js` with any provider that returns an audio stream. The client just calls `/api/tts` and plays the blob.
- STT: replace `stt.js` with any provider that accepts an audio file and returns `{text}`. The vocabulary keyterm-prompting feature is ElevenLabs-specific and can be removed if switching.

### Adding More Languages
The feedback is currently always in Korean. To support other languages:
- Add a `feedback_language` field to sessions
- Pass it to `feedback.js` and make the Korean instructions conditional
- The `overall`, `what_worked`, `needs_improvement` fields should be in whatever language is configured
- `original` and `corrected` always stay in English

### Extending the Task Model
The current task has: title, topic, objectives, vocabulary, language_forms, persona_name. To add a difficulty rating, target grammar level (CEFR), or lesson type, add the column to the schema and the DB migration in `ensureReady()`, then add the field to the task creation form and the system prompt builder.
